# NPPS4 v5.25 专用饰品制作与转移契约修复

Build ID：`v5.25-special-accessory-card-grant-and-transfer-contract-fix`

## 修复范围

本版不修改已经正常工作的通用饰品链路，只修正 CN/GL 角色专用饰品。

### 1. LOVEARROWSHOOT 缺少专用饰品目标卡

v5.24 在某个专用饰品目标卡尚未存在于玩家数据库时，会先建立一个尚未 flush 的 SQLAlchemy `Unit` 对象。此时 `id` 仍为 `None`，旧代码随即执行 `int(row.id)`，触发 `TypeError`。外围测试兑换码将异常转为警告，因此兑换仍显示成功，但从第一个缺卡目标起，其余目标卡全部没有补齐。

v5.25：

- 待写入对象不会再执行 `int(None)`；
- 最终统一 flush；
- 写入后重新查询全部目标卡；
- 每一个当前 Profile 的专用饰品目标 UR 必须有至少三张可消耗/装备副本；
- 任一目标不足都会在兑换结果中明确列出 Unit ID 与实际数量，不再静默跳过。

精确客户端 Master 已核对：CN 258 条、GL 484 条映射的目标卡全部真实存在。截图中的 GL 目标为：

- 饰品 424 → Unit 3809（[Chara Pop Fes 2] Rina Tennoji）
- 饰品 462 → Unit 3920（[A Day Off - μ's] Honoka Kosaka）
- 饰品 479 → Unit 3927（[New Year at Kanda Shrine] Honoka Kosaka）

### 2. 新制作专用饰品不显示、旧饰品显示 MAX

旧 `LOVEARROWSHOOT` 会直接建立并升满所有饰品，包括本应使用两张指定 UR 制作的专用饰品。因此玩家数据库中已经存在一份人工生成的等级 8/MAX 副本。与此同时，真正制作出的等级 1 专用饰品在未满绝对等级上限前，只能装备给 `accessory_special_m` 指定的那张卡。制作消耗两张卡后，如果测试码没有留下第三张目标卡，等级 1 饰品就不会出现在其他同角色卡的装备候选中；装备界面能看到的往往只是旧的人工 MAX 副本。

v5.25：

- `LOVEARROWSHOOT` 只自动建立并升满通用饰品；
- 不再直接建立或升级任何专用饰品；
- 专用饰品必须继续通过“两张精确目标 UR → 一件等级 1 饰品”的正常流程获得；
- 新制作饰品序列化为 `level=1`、`max_level=4`、`rank_up_count=0`；
- 测试码保证制作后仍剩一张精确目标卡，用于立即装备该等级 1 饰品。

### 3. 清理旧版人工 MAX 专用饰品

由于 v5.24 没有记录饰品来源，升级时不能自动判断某一件 MAX 饰品究竟是玩家正常升级还是旧测试码生成。为避免静默破坏玩家资产，本版增加显式测试清理码：

`LOVEARROWSPECIALCLEAN`

它只删除：

- 当前 Profile 的专用饰品；
- 已达到绝对等级上限；
- 未收藏；
- 未装备。

等级 1 的真实制作副本、收藏饰品和已装备饰品全部保留。清理后再输入 `LOVEARROWSHOOT` 补齐目标卡即可。

### 4. 已装备饰品是否应该锁定

互联网保存的攻略和游戏帮助转述能够确认：饰品从社员详情界面进行“装备/卸下”，专用饰品由两张指定 UR 制作，初始上限为等级 4、重制后可到等级 8；但这些页面没有明确说明“跨社员换装是否必须先手动卸下”。

对本项目上传的最终 CN 与 GL APK 解密 Lua 后，两边 `AccessoryModel.wear` 的行为完全一致：当选中的饰品已装备给另一张卡时，客户端会在同一个 `unitWearAccessory` 请求中同时发送旧绑定到 `remove`，并发送新绑定到 `wear`。因此客户端官方实现就是一次操作完成原卡卸下和新卡装备，并非先灰锁、再要求用户返回旧卡手动卸下。

v5.25 保留直接转移，但服务端不再自行猜测并删除旧绑定：

- 正常 CN/GL 客户端发送 `remove + wear`，一次请求完成转移；
- 自定义或损坏客户端只发送 `wear` 时，服务端拒绝操作；
- 同一件饰品仍只能绑定一张卡，同一张卡仍只能装备一件饰品。

## 兼容性

- 无数据库迁移；
- Museum 保持纯相册模式；
- 排名保持原始共享原分结构；
- PC 与 Android 使用同一套 Python 服务端；
- 精确 CN/GL Unit 与饰品 Master 仍完全内置在服务端包中。
